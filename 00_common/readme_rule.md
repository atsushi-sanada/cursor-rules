# README 作成ルール

エディタ/IDE での README 作成における共通ルール。README は入口説明書として「概要」と「最低限の使い方」に特化し、細かい仕様はコードコメントへ逃がす構成にします。

---

## 基本方針

- **入口説明書としての役割**：プロジェクトの概要と最短で使えるまでの情報に特化
- **対象**：非エンジニアの新卒でも理解できる説明書
- **簡潔性**：長くなりすぎず、更新しやすい構成を維持
- **詳細はコードへ**：細かい仕様やロジックはコード内のドキュメンテーションを参照

---

## README テンプレート

```markdown
# プロジェクト名

<!-- 例：ガチャ分析ツール / シミュレーション自動化スクリプト -->

## 概要

<!-- プロジェクトの目的・何ができるかを2〜4行で簡潔に説明（要約） -->

### このツールについて

<!-- 添付例のように、最初に期待値を揃えて迷いを減らす -->

- **できること（1機能1行）**
  - <!-- 例：CSVを検証して、登録用TSVを自動生成する -->
  - <!-- 例：設定ファイルを読み込み、環境ごとの差分を自動で切り替える -->
  - <!-- 例：ブラウザでログインして、指定ページまで自動で移動する -->
  - <!-- 例：入力データの不備を検出し、修正ポイントをレポートする -->

---

## クイックスタート

<!-- 最短で「動かす/使う」までの手順だけを書く（詳細は後続セクションへ誘導） -->

### 初回のみ

1. <!-- 例：config.example をコピーして config を作成 -->
2. <!-- 例：依存関係をインストール -->
3. <!-- 例：初回の動作確認を実行 -->

### 毎回

1. <!-- 例：実行コマンド or 実行ファイルを起動 -->
2. <!-- 例：入力ファイルを用意して実行 -->
3. <!-- 例：結果の確認 -->

---

## セットアップ

<!-- "最短で使えるまで" に必要なステップだけを書く。細かい説明は不要 -->

---

## 使い方

<!-- 「どう動かすか」ではなく「どう使うと目的が達成できるか」を中心に -->

---

## その他

<!-- READMEが複雑にならないよう、補足情報はここに最低限まとめる -->
<!-- TIPSやオプションなど -->

### その他の詳細について

- 個別の仕様や詳細なロジックは、**プロジェクト内の各コードのドキュメンテーションを参照**してください
- README はあくまで「最短で触れるための入口」です
```

## 構成の考え方

### この 5 項目だけで十分な理由

1. **新人が知りたいのは「何のプロジェクトか」が中心**

   - 概要があれば目的が明確になる

2. **技術詳細はコードに記述したほうが最新状態に保ちやすい**

   - README に詳細を書くと更新漏れが発生しやすい

3. **README が長くなると更新されず役に立たない**

   - 簡潔に保つことでメンテナンス性が向上

4. **最短の導線（クイックスタート）があると離脱が減る**
   - 初回のみ / 毎回 を分けることで、手順が迷子になりにくい

5. **最低限「概要・クイックスタート・セットアップ・使い方」さえあれば、誰でも触れる**
   - 入口としての役割を果たせる

---

## 必須セクション

以下の 5 セクションを必ず含める：

1. **概要**：プロジェクトの目的と機能を 2〜4 行で簡潔に説明
2. **クイックスタート**：最短で動かすための手順（**初回のみ / 毎回** を分けて記載）
3. **セットアップ**：初回に必要な準備手順（3〜5 ステップ）
4. **使い方**：目的達成のための基本的な使い方
5. **その他**：TIPS、オプション、詳細情報への参照

---

## 記述ルール

### 概要セクション

- **最初に 2〜4 行で要約**：長文は避ける（ここは“要約”として固定）
- **目的と機能を明確に**：何ができるかを最初に示す
- **ターゲット読者を意識**：誰が使うツールかを示す
- **「このツールについて」を置く**：期待値を揃え、読み手が成功体験を想像できるようにする
  - **できること（1機能1行）**を箇条書きで列挙（抽象説明より具体的な成果を書く）
  - 重要な制約や注意がある場合のみ、**1行で追記**する（例：対象外機能、実行環境、再実行時の注意）
  - 設定変更が必要な場合のみ、**どこを変えるかを1行で明記**し、参照先セクションへ誘導する

### クイックスタートセクション

- **初回のみ / 毎回 を分ける**：読者が「今やること」だけを追える構成にする
- **最短に絞る**：各ブロックは **1〜3 ステップ**を目安（詳細は後続セクションへ誘導）
- **実行方法を明確に**：コマンド or ダブルクリック等、手段を曖昧にしない
- **詳細へ誘導する**：設定が絡む場合は「セットアップ」「使い方」「その他」へリンク/参照を書く

### セットアップセクション

- **前提条件を明記**：必要なツール・環境を最初に示す
- **手順は 3〜5 ステップに収める**：多すぎると読者が離脱する
- **コマンドはコードブロックで記載**：コピペしやすくする
- **詳細はコードへ逃がす**：設定の詳細はコード内コメントを参照

### 使い方セクション

- **目的達成の流れを中心に**：技術的な操作手順より、どう使うと目的が達成できるかを重視
- **ステップバイステップで記載**：番号付きリストで明確に
- **具体例を含める**：抽象的な説明より具体例が理解しやすい

### その他セクション

- **TIPS**：よくある問題と解決方法
- **オプション**：開発モードやテスト実行など
- **詳細情報への参照**：コード内ドキュメンテーションへの誘導

## 品質チェックリスト

- [ ] 概要が 2〜4 行で簡潔に書かれているか
- [ ] 概要内に「このツールについて」があり、「できること（1機能1行）」が列挙されているか
- [ ] 重要な制約/注意や設定変更が必要な場合、それが1行で明記されているか
- [ ] クイックスタートがあり、「初回のみ / 毎回」が分かれているか
- [ ] セットアップ手順が 3〜5 ステップに収まっているか
- [ ] 前提条件（必要なツール・環境）が明記されているか
- [ ] 使い方が目的達成の流れで書かれているか
- [ ] コマンドがコードブロックで記載されているか
- [ ] 詳細な仕様がコード内コメントへ逃がされているか
- [ ] README が長すぎず、更新しやすい構成になっているか
- [ ] Markdown 記法ルールに準拠しているか（見出し階層、コードブロックなど）
