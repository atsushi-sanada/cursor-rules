# フォルダ命名規則

## 命名の目的

- 構造を見ただけで内容が把握できる
- 並び順や分類のルールを明確にする
- メンバーが迷わずファイルを格納・参照できる

---

## 結論（迷ったらこれ）

**フォルダ名もファイル名と同じ考え方で「小文字・区切り記号・意味が一目で分かる」形に統一します。**

- **原則**: **英小文字＋`_`区切り（snake_case）**
- **重要**: **1 プロジェクト 1 ルール（混在しない）**

---

## 用語の補足（最小限）

- **フォルダ名**: ディレクトリ名（ファイルの入れ物）
- **パス**: フォルダの道筋（例: `assets_images/ui_icons/`）

---

## 基本ルール

- **英小文字（半角英数字）のみを使用**
- **単語の区切りは `_`（アンダースコア）で統一**
- **スペース・日本語・特殊記号は禁止**
- **カテゴリや目的ごとにプレフィックスを使用**
- **用途ごとに階層化しすぎない（2〜3 階層が目安）**

---

## 命名パターン

```

\[カテゴリ]_\[内容]
または
\[目的]_\[対象]

```

### 補足ルール（実務で効く）

- **単数形/複数形を統一**: フォルダは基本 **複数形**（例: `assets_images`, `assets_icons`）
- **日付/バージョンは入れない**: 履歴は Git やファイル名側で管理する

---

## 例：使用頻度の高いフォルダ名

| フォルダ名        | 用途                                 |
| ----------------- | ------------------------------------ |
| `design_psd`      | デザインの元ファイル（Photoshop 等） |
| `design_export`   | 書き出し済み画像・納品用アセット     |
| `spec_docs`       | 仕様書（PDF・Markdown）              |
| `scripts_deploy`  | デプロイ・ビルド系スクリプト         |
| `docs_meeting`    | 議事録や会議資料                     |
| `assets_images`   | 画像素材（JPG/PNG など）             |
| `assets_icons`    | アイコン系素材（SVG/PNG）            |
| `dev_html`        | 開発中の HTML ファイル群             |
| `archive_2024_q2` | アーカイブ（四半期ごとなど）         |

## NG 命名例と理由

| NG 例               | 理由                                          |
| ------------------- | --------------------------------------------- |
| `新しいフォルダ`    | 意味が伝わらず混乱する                        |
| `aaa` / `temp`      | 中身が分からない・破棄忘れがち                |
| `デザイン` / `資料` | 日本語は検索しづらく環境依存あり              |
| `img_folder_1`      | 連番はスケーラビリティに欠ける                |
| `ui-assets_v3`      | 区切り混在/バージョン混入で運用が破綻しやすい |
| `asset icon`        | スペースは事故源                              |
| `UIAssets`          | 大文字混在は差分/運用で混乱しやすい           |

---

## 命名補足ルール

- 時系列で管理したい場合は `archive_yyyy_mm` や `release_2024_q1` などを使用
- 共通リソースは `common_` プレフィックスで管理（例：`common_components`, `common_assets`）
- 一時ファイルは `temp/` に明示的に集約しておき、定期削除ルールを設けると ◎

---

## 例外と運用ガイド

- **原則**: 新規フォルダは英小文字＋`_` で作成する。ツールやプラットフォームが特定名称を要求する場合のみ例外を許可する。
- **例外の扱い**: 例外フォルダは明示的に例外リストへ登録し、理由（ツール名・必須性）を記載する（例外リストは本書で管理する）。
  - 例: `Assets/`, `ProjectSettings/`, `Packages/`（Unity）、`Sources/`, `Project.xcodeproj`（Xcode）、`go.mod`, `Cargo.toml`（言語仕様のファイル名）
- **命名一貫性**: 例外は最小限に留め、ドキュメント化した上でチーム全体に周知すること。
- **移行時の注意（既存リポジトリ）**: Windows は大文字小文字を区別しない設定が多いため、大文字 → 小文字の変更は `git mv` を使って一旦別名へリネームしてから最終名に変更する（例: `git mv Assets temp_assets && git mv temp_assets assets`）。PR で影響範囲を明示し、CI で参照整合性を確認する。
- **運用チェック**: 新しい例外を追加する際はコードオーナー／リポジトリ管理者の承認を必須とする。
